---
title: Roadmap
description: What Raven should build next to make the compiler derive TypeScript-like types automatically.
---

Raven is pre-1.0. The priority is compiler intelligence: infer more from data,
flow, and project structure before adding developer-facing type syntax.

See [Type Intelligence](/docs/type-intelligence) for the design principle and
[Compiler Architecture](/docs/compiler) for where the pieces live.

## Now: Layer 2 type engine

Recently added foundations:

- exact type identity via `sameType`
- value compatibility via `isAssignableTo`
- internal optional types, e.g. `number?`
- internal unions, e.g. `number | string`
- best-common-type inference for mixed arrays and record arrays with missing
  fields
- inferred union return types for unannotated functions

Next improvements:

- source-aware diagnostics for assignability failures
- clearer missing-field and union-branch explanations
- parser support for the smallest optional/union annotation syntax only where
  inference cannot know intent

## Next: Layer 3 flow engine

Flow narrowing depends on union types. Once the type engine is stable, Raven
should narrow variables inside branches:

```lua
if typeof value == "string" then
  print(value)
end
```

Inside the branch, `value` should be treated as `string`.

## Then: Layer 4 project engine

The workspace registry already proves the project-wide model: publish once, use
everywhere, no type import. The next step is extending that pattern to more
inferred API shapes:

- top-level function signatures
- inferred module boundaries
- package-visible compiler metadata

## Later: library and backend intelligence

After Layers 2–4 are stronger, Raven packages should become self-describing by
shipping compiler-generated API metadata instead of hand-written declaration
files. Backend integrations such as HTTP, database, auth, queues, CLI, and
filesystem should verify external shapes at the boundary.

## Not yet

Avoid these until the compiler can reason about them internally:

- `interface`
- generics/type parameters
- `keyof`
- mapped or conditional types
- frontend/DOM type work

## Known cleanup items

- Decide whether old examples using `val` should be rewritten to `let`/`const`
  or whether `val` should become a real keyword.
- Decide whether `fn ... do` should parse or examples should use the current
  `fn ...` body form.
- Make `raven version` read from package metadata instead of a hardcoded string.
