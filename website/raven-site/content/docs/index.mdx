## The problem it solves

Every language with static types eventually asks you to write the same shape twice: once as data, once as a type.

```ts
// Without inference
type User = { id: number; name: string }
const user: User = { id: 1, name: "Bro" }
```

```lua
// With Raven
let user = { id: 1, name: "Bro" }
```

The compiler already knows `user` is `{ id: number, name: string }`. No annotation, no interface, no duplication — you wrote the data once, and that's the only place you had to write it.

## How it works

Raven has exactly two levels of scope for inferred types, and the whole language design sits on top of this one distinction.

**`let` / `const`** — local. The shape is inferred and stays inside the file it's declared in.

**`model`** — published. The shape is inferred (or bound to an external source) and becomes available to the *entire project*, no import required.

```lua
// user.rv
model user = { id: 1, name: "Bro" }
```

```lua
// auth.rv
fn login(user)
    print(user.name)
end
```

`auth.rv` never imports a type. The compiler looks up `user` in the project's **workspace registry**, finds the shape published in `user.rv`, and type-checks against it directly.

Imports still exist in Raven — they're just for *code*, not types:

```lua
import login from "./auth"
```

What Raven removes is the `import type { User } from "./types"` line, not imports in general.

## Concepts

### Publishing a shape with `model`

Any file can publish a shape once, and every other file in the project can use it by name — no import, no re-declaration.

### Binding external data

The same `model` keyword also binds a name to an external source — a database, an API, a JSON file — anywhere the compiler can't infer a shape from source alone:

```lua
model User = database.users
model User = api("/users")
```

This is the one place Raven asks you to be explicit, because the data genuinely doesn't originate in your project.

### One shape per name

If two files publish `model` under the same name with different shapes, that's a compile error — not a silent merge, not an override:

One name, one canonical shape, project-wide. If you need a different shape, give it a different name.

## Philosophy

> The programmer describes the data. The compiler manages the types.

Writing Raven only ever asks you to make two decisions:

1. Should this shape stay local (`let`), or be shared project-wide (`model`)?
2. Is this data coming from outside the project — and if so, what shape does it have?

Inference, propagation, and validation are the compiler's job, not yours.
