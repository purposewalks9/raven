## Analysis

Per-op averages are sub-millisecond for every single-file stage; at current fixture scale the compiler is fast in absolute terms.
The decisive signal is the workspace: `check (buildProject)` — which performs the cross-file `model` resolution through the shared `WorkspaceRegistry` — accounts for ~94% of wall time across the multi-file workspace, versus ~3% (`parse`) and ~3% (`lex`). This matches the design hypothesis in SYSTEM_DESIGN.md §2: the typechecker is the only stage doing cross-file work and is the most plausible bottleneck as projects grow.

**Phase 0 exit criterion:** a single stage (`check`/buildProject) is a clear majority (>50%) of wall time on the large workspace fixture. Recommendation per SYSTEM_DESIGN.md `Phase 1` is to port the **typechecker** to `raven-core` first, introducing the type-interning table for structural equality.

## Phase 1 addendum — FFI marshalling cost (2026-09-05)

Since the Phase-1 port, `check` runs in `raven-core` via the `raven-node`
napi binding; the per-stage figures above now include the JSON round trip the
TS wrapper pays on both sides of the boundary. The checker **engine** is
29 µs / 934 µs (small/medium) in-process — comparable to the old TS checker —
while ~91% of the medium-file `check` cost is serde_json re-parse of the AST +
result `Value` assembly + re-serialization. See
[`phase1-ffi-analysis.md`](./phase1-ffi-analysis.md) for the per-phase
breakdown. This is precisely the outcome SYSTEM_DESIGN.md §5 Phase 1 expects
("only move to a binary format if Phase-1 benchmarks show serialization itself
is a cost"); the fix is Phase 2's *source text in → typed AST out* boundary.
