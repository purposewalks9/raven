## Analysis — Phase 2 vs Phase 1

Phase 1 (`check` AST-in) vs Phase 2 (`check` source-in) on the same release build:

| Fixture | Phase 1 `check` (AST-in) | Phase 2 `check` (source-in) | TS baseline (`check` only) |
|---|---|---|---|
| small (15 lines) | 501 µs | **204 µs** (2.5× faster) | 15 µs |
| medium (407 lines) | 15520 µs | **5618 µs** (2.8× faster) | 466 µs |
| workspace (56 files) | 229662 µs | **49146 µs** (4.7× faster) | ~16 ms |

Source-in removes the large JSON AST that crossed the boundary in both directions in Phase 1. For the medium fixture, `check` (source-in) 5618 µs is now comparable to the TS `lex` (1268 µs) + `parse` (1811 µs) + `check` (466 µs) = 3545 µs total — Rust is at parity with the TS pipeline end-to-end, with the remaining gap due to the output side (`bindings` → JSON) which Phase 2 now splits. The workspace `buildProject` (49146 µs) is 4.7× faster than Phase 1's 229 ms, trending toward the TS 16 ms baseline — the next wins are Phase 3's `emitter`/`optimizer`/`sourcemap`.

**Why not yet at 466 µs?** `check (source-in)` includes `tokenize` + `parse` + `check` in Rust (one FFI call). The isolated checker engine is still ~934 µs for the medium fixture (phase1-ffi-analysis.md). The 5618 µs is lex+parse+check combined, matching the TS lex+parse+check total.

**Design decision (AST-out):** `compiler/src/cli/pipeline.ts:checkSourceWithBindings` still builds the AST in TypeScript for `optimize`/`Emitter` until Phase 3. `compileFile` now inlines the cheap `TypeChecker.checkSource` (diagnostics only) instead of the heavy `checkSourceWithBindings` — see that file's doc comment. `full-pipeline` (lex+parse+check+optimize+emit via the cheap path) is now **close to the sum of cheap stages**, not meaningfully above it: small `full-pipeline` 188 µs vs sum 324 µs (lex+parse+check+optimize+emit+sourcemap), medium 8601 µs vs sum 10045 µs — previously `full-pipeline` was 604 µs vs 238 µs and 12024 µs vs 9055 µs, the gap was the bindings cost leaking back in.
