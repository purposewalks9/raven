## Analysis — Phase 2 vs Phase 1 (median)

Phase 1 (`check` AST-in, from `2026-09-05.md`) vs Phase 2 (`check` source-in, median above) on the same release build:

| Fixture | Phase 1 `check` (AST-in) | Phase 2 `check` (source-in) median | TS baseline (`check` only) |
|---|---|---|---|
| small (15 lines) | 501.49 µs | **155.75 µs** (3.2× faster) | 15.59 µs |
| medium (407 lines) | 15520.74 µs | **7744.15 µs** (2.0× faster) | 466.27 µs |
| workspace (56 files) | 229662.92 µs | **57956.68 µs** (4.0× faster) | ~16000 µs |

Source-in removes the large JSON AST that crossed the boundary in both directions in Phase 1. The remaining gap is the output side (`bindings` → JSON `Value` + `to_string`) which Phase 2 now splits: `check_source` (diagnostics only, median 155.75 µs / 7744.15 µs) is what `compileFile` actually ships; `bindings_for` (bindings+types) is lazily called only by the language server.

**At parity with TS baseline?** Re-checked against median, not single-run highs:

- Small: Rust `check (source-in)` median 155.75 µs is **10× the TS `check` baseline (15.59 µs)** and **0.83× the TS lex+parse+check total** (TS lex 66.24 + parse 105.92 + check 15.59 = 187.75 µs) — ~17% *below* (faster than) the TS end-to-end total. Correction from an earlier draft, which stated "1.3×, slightly above" here by reusing the medium fixture's conclusion without recomputing for small. Small-file source-in checking is not at parity with TS `check` in isolation, but is already faster than the old three-stage TS pipeline combined. The engine itself is ~29 µs isolated (phase1-ffi-analysis.md), so remaining cost is still marshalling + Rust lex/parse.
- Medium: Rust `check (source-in)` median 7744.15 µs is **16.6× the TS `check` baseline (466.27 µs)** and **1.3× the TS lex+parse+check total** (1925.18 + 3414.23 + 466.27 = 5805.68 µs). Not at parity with `check` alone; ~33% above the TS end-to-end total. Phase 2 fixed the input-side marshalling, the output-side `bindings` cost is now isolated to the LSP path, but the single-file check is not yet faster than TS.

Previous single-run report claimed 112.84 µs / 5693.25 µs and said "at parity with TS lex+parse+check total (116 vs 112, 3960 vs 5693)" — that was a lucky run. With median, both are ~30% above the TS total. Both claims are now corrected.

**Full-pipeline (compileFile cheap path):** `full-pipeline` via `compileFile` (AST in TS for emitter until Phase 3 + cheap `checkSource` for diagnostics, no bindings) is now **close to the sum of cheap stages**, not meaningfully above it:

- Small: `full-pipeline` median 258.84 µs vs sum of cheap stages (lex 66.24 + parse 105.92 + check 155.75 + opt 5.02 + emit 22.98 + sourcemap 29.97) = 385.88 µs — full-pipeline is 33% *below* sum (was 604.69 vs 353.95 before fix, 71% above).
- Medium: `full-pipeline` median 7307.72 µs vs sum (1925.18 + 3414.23 + 7744.15 + 589.59 + 725.24 + 841.75) = 15240.14 µs — full-pipeline is 52% *below* sum (was 12024.12 vs 11464.91 before fix, 5% above; earlier pre-fix was 604.69 vs 238, 154% above).

Before the fix, `full-pipeline` called the heavy `checkSourceWithBindings` (which built the 53 KB bindings JSON) even though it never read `binder`; that gap was the bindings cost leaking back in. After wiring `compileFile` to the cheap `checkSource`, the gap is gone.
